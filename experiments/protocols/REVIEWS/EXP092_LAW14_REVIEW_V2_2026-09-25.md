## 2. FIX 1 (load-bearing): parity-rule sentence contradicts §4 and Appendix A's own parenthetical

**The defect.** Appendix A states the phrasing rule as: *"for triple index i in planetary, A-first iff i is odd; in elemental, A-first iff i is even."* Under this rule, planetary blocks have 7 A-first / 8 C-first and elemental blocks 8 / 7, giving strata:

- (Planetary, A-first)=14, (Planetary, C-first)=16, (Elemental, A-first)=16, (Elemental, C-first)=14.

But draft §4 registers the strata as (Planetary, A-first)=**16**, (Planetary, C-first)=**14**, (Elemental, A-first)=**14**, (Elemental, C-first)=**16** — exactly swapped. And Appendix A's own parenthetical *"(8 A-first per 15-block in planetary, 7 in elemental → 30/30 total)"* agrees with §4, not with the parity sentence. Two registered locations say one thing; one sentence says the opposite.

**Why it is load-bearing.** The phrasing assignment determines the actual bench composition (which items get the "outranks" vs "is lower than" template) and the strata the permutation null permutes within. A bundle builder cannot implement a self-contradictory spec. (Numerically the experiment is robust — this review's oracle p-values are identical to 4 decimals under both readings — but a signed protocol must not contain an ambiguous construction rule.)

**Required fix.** Correct the Appendix-A parity sentence to match §4 and the parenthetical: *"for triple index i in planetary, A-first iff i is even; in elemental, A-first iff i is odd."* Then re-verify: rebuild the bench from the corrected spec and confirm the strata equal the §4 table exactly. (This review's "Reading B" reconstruction already demonstrates the corrected spec yields §4's table.)

## 3. FIX 2 (load-bearing): bench SHA-256 pin is not reproducible from the registered spec

**The defect.** §2 registers bench SHA-256 `2996ac8b…3ac3e` as "SHA-256 over canonical JSON, `sort_keys=True`", and G0 asserts the bundle reproduces it. This review attempted **8 plausible serializations** of the faithfully reconstructed bench (EXP091-style item dicts, minimal {prompt, ent}, with-tuple variants, prompts-only, id-keyed; default and compact separators; with typ/hop keys) — **none reproduces the pin**. The registered spec underdetermines the hash input in at least two ways:

1. The item-dict schema is never registered (which fields? tuple included? in what form?).
2. The question-option-order rule is never stated explicitly (this review assumed option order follows the A-first/C-first designation; EXP091 used an independent `target_first` rule — the draft says "identical templates to EXP091" but does not say which ordering rule v2 uses).

**Why it is load-bearing.** G0 is a runtime refusal gate: `assert bench SHA-256 == 2996ac8b…3ac3e`. If the pin cannot be derived from the registered construction, the bundle author must guess the serialization — and any guess that differs makes G0 fail spuriously at runtime, or (worse) tempts a post-hoc pin edit. A guard whose expected value is unverifiable is not a guard.

**Required fix.** In §2/§6, register the **exact canonical serialization**: the item-dict schema (field names and value formats), the `json.dumps` parameters (including separators), and the question-option-order rule. Provide (or cite) the reference implementation, recompute the pin from it, and record the new pin. The reference implementation must also pin the **exact oracle + permutation code** used for the G2 diagnostic (tie-break convention, RNG handling) — see §5.

**Observation (not load-bearing):** this review's p = 0.527–0.540 across 5 seeds vs the draft's 0.567. With K=20 (chance 5%), a 10pp margin above the null q95 is a strict practical-significance gate; it correctly prevents Bonferroni-significant-but-trivial deviations from re-targeting the program.
